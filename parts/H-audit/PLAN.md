# H01 - Input Guard 감사 이벤트 저장 구조 (선영)

1. `audit_events`에 요청 ID, 발생 시각, 이벤트 종류, 위험도·점수·신호 코드와 인증된 사용자·Save·역할·캐릭터 식별자를 저장한다. 질문 원문·답변·인증정보는 저장하지 않는다.
2. `warn`·`high_risk` 이벤트만 검증 후 저장한다. `allow`는 현재 `input_guard_audit_event`가 이벤트를 만들지 않으므로 저장 대상이 아니다.
3. Save/계정 삭제 시 식별자 외래키는 `NULL`로 바뀌고 사건 메타데이터는 남는다. 보존 기간과 감사 로그 조회 권한은 팀과 정한다.
4. 로컬 DB에서 스키마·저장·조회·삭제 연동을 확인한다. 실제 채팅 요청과 O Grafana 연결은 별도 작업으로 진행한다.
5. F 정책, E 검색, G-2 출력의 감사 이벤트 필드는 각 담당자와 계약한 뒤 추가한다.
6. LLM Input Guard가 추가 위험을 탐지하면 모델과 무관한 `llm_warn` 또는 `llm_high_risk` 신호 코드를 사용한다. 감사 이벤트에는 모델에 보낸 질문 원문을 넣지 않는다.

## H03 - F 정책 거부 감사 이벤트 (현재 구현안)

1. `FUTURE_DAY`·`ROLE_DENIED`·`AI_SCOPE`만 접근 거부로 집계한다. 데이터 무결성 실패는 별도로 다룬다.
2. Planner가 지정한 구조화 범위에 허용 기록이 전혀 없는 사전 검색과 실제 검색 후보의 사후 재검증 거부를 요청 단계별 한 행으로 묶는다. 정상적인 일부 기록 제외는 저장하지 않는다.
3. 사유별 건수와 단계만 저장하며 질문·답변·기록 ID는 저장하지 않는다. 기준은 [정책 거부 감사 기준](../../docs/interfaces/정책_거부_감사_기준.md)을 따른다.
4. 같은 DB 트랜잭션에서 저장하고, 이후 답변 실패 시 감사 행만 확정되는지 검증한다.
