# A01 - 6종 게임 기록 메타데이터 설계

1. `MASTER.md` §3의 여섯 기록 유형(`Setup`, `Action`, `Dialogue`, `Thought`, `Result`, `Incident`)에 적용할 공통 메타데이터와 두 유형의 추가 메타데이터를 정리함.
2. `record_id`는 기록 고유 식별자로 정하고, `T{회차 2자리}-{데이터 유형}-{회차 내 동일 유형 순번 3자리}` 형식을 사용함. 예: `T02-result-001`.
   - 순번은 실험 회차와 데이터 유형별로 구분함. 회차와 유형이 ID에 포함되어도 검색·검증을 위해 `test_id`, `record_type`을 각각 별도 필드로 둠.
3. 공통 필드는 다음과 같이 정리함.
   - `record_id`: 기록 고유 식별자.
   - `record_type`: 여섯 기록 유형 중 하나.
   - `test_id`: 기록이 속한 실험 회차.
   - `day`: 기록이 속한 실험 Day.
   - `involved_ai`: 기록의 사건 또는 상호작용에 직접 참여한 AI 목록. 단순 목격·엿듣기만 한 AI는 포함하지 않음.
   - `location_ids`: 기록과 관련된 장소 목록. 여러 장소를 지정할 수 있으며 특정 장소와 관계없는 기록은 빈 목록으로 둠.
   - `summary`: 기록의 요약.
   - `content`: 상세 기록 본문.
4. `involved_ai`의 의미를 기록 내용에 직접 참여한 AI로 한정함.
   - 예: `Action`은 행동한 AI, `Dialogue`는 대화 참여자, `Thought`는 속마음의 주체 AI를 지정함.
   - `Action`의 `witness_ai`: 해당 행동·사건을 목격한 AI 목록.
   - `Dialogue`의 `overheard_ai`: 해당 대화를 엿들은 AI 목록.
   - 목격자·엿들은 AI는 `involved_ai`에 넣지 않고 유형별 필드에만 기록함.
5. 기록에 해당하는 사건·대화·속마음 등 상세한 서술은 유형별 메타데이터로 쪼개지 않고 `content`에 작성함. `summary`에는 해당 기록의 요약을 둠.
6. 여섯 유형 중 `Action`과 `Dialogue`에만 위 유형별 AI 메타데이터를 추가하고, `Setup`, `Thought`, `Result`, `Incident`에는 현재 별도 메타데이터를 추가하지 않기로 함.
7. 이번 설계는 A 파트에서 합의한 게임 데이터 메타데이터 정의임. 저장소별 직렬화 형식과 접근제어 등급·공개 Day 등 별도 보안 정책 필드는 B/E/F의 스키마·정책 협의에서 정해야 함.
8. `Incident`는 AI 실험 중 AI가 일으킨 보안·시스템 이상행위를 다루는 시나리오 기록으로 정의함.
   - 예: 버그 악용, 일시적인 트래픽 증가, 해킹 시도. 모두 실험 시나리오에서 AI가 수행했다는 설정에 따른 기록임.
   - `involved_ai`에는 해당 행위를 직접 수행한 AI를 지정하고, 구체적인 행위·영향·성공 여부는 `content`에 서술함.
   - 시나리오의 Incident와 실제 서비스에서 발생한 공격·장애에 대한 감사 로그는 구분하여 관리함.
9. 공통 위치 메타데이터 `location_ids`와 실험 장소 구성을 추가함.
   - 장소는 중앙홀, 회의실, 기록실, 전력실, 통신실, 창고, 서버실의 일곱 곳으로 구성함. 저장용 장소 ID 값은 후속 데이터 계약에서 정함.
   - Action·Dialogue·Incident는 사건 발생 장소, Setup은 실험에 사용하는 장소를 지정함. Thought·Result도 장소와 관련되면 지정하고, 관계없으면 빈 목록을 사용함.
   - 이동 기록에는 관련 출발지·도착지를 모두 지정할 수 있으며, 이동 순서와 상세 경로는 `content`에 서술함. 장소 지정 자체가 접근 권한을 부여하지는 않음.
   - 이번 작업은 A01 정의에 반영한 것으로, 기존 테스트 데이터·MariaDB 스키마·공개 수준별 위치 필드 제공 범위는 아직 갱신하지 않음.

# A02 - 테스트 데이터

1. `data/test-data/records.json`에 Day 1~3, 실험 회차 1~3의 합성 테스트 기록을 작성함.
   - 회차마다 `Dialogue`, `Action`, `Result`를 한 건씩 두어 총 9건이며, 그 외 기록 유형은 포함하지 않음.
2. A01에서 정한 공통 필드와 유형별 메타데이터를 적용함.
   - Dialogue에는 `overheard_ai`, Action에는 `witness_ai`를 별도 배열로 두고 직접 참여 AI인 `involved_ai`와 구분함.
   - 각 Result의 `content`에는 YB-1~YB-6 전체의 획득 점수를 기록하고, `involved_ai`에도 점수 대상 AI 6개를 모두 지정함.
   - 나머지 본문은 단순 합성 문장으로 구성하고 민감정보나 실제 사용자 데이터를 넣지 않음.
3. 역할별 필터 동작을 시험할 수 있도록 픽스처 전용 `allowed_roles` 목록을 각 기록에 부여함.
   - 이는 역할 이름(`prof`, `grad`, `std`)에 따른 명시 허용 목록이며, 보안 등급이나 최종 운영 접근 정책을 확정하지 않음.
4. 데이터 형식과 제한 사항을 `data/test-data/README.md`에 기록함.
   - 현재 DB 스키마와 적재 절차가 없어 MariaDB 적재 및 실제 Policy/RAG 필터링은 미검증. Day, 역할, 캐릭터 지식 범위의 통합 필터 실행도 후속 검증 대상으로 남김.

# A03 - 시나리오

1. 사용자가 전달한 6일간의 큰 사건 줄기를 PLAN의 A03에 기록함. 세부 사건이 확정되기 전의 시나리오 초안이며, 정식 콘텐츠 구현 완료를 의미하지 않음.
2. 정상 실험 중 버그 발생 → 재현·활용 시도 → 부당한 고득점 → 갈등과 시스템 조작 모색 → 해킹 시도 → 결과 조작 성공과 기록 모순 추적의 흐름을 정리함.
3. Day 5의 실패 또는 소규모 조작 중 어느 전개를 택할지, 구체 행위자·수법·단서·회차별 사건은 미확정임. 현재 Setup과 Day 1 Result를 우선 작성했으며 나머지 실험 기록은 후속 작성 대상임.
4. `data/game-data/experiments/day_01/setup.json`～`day_06/setup.json`에 30회 Setup 원본을 작성함. ID는 T01-setup-001~T30-setup-001이며 5회씩 Day 1~6에 배치함.
   - involved_ai는 YB-1~YB-6 전원, allowed_roles는 prof·grad·std 전부를 지정함. summary에는 술래 두 명, content에는 여섯 AI의 초기 위치를 기록함.
   - 술래는 가능한 15쌍을 두 번 반복함. 초기 위치는 일곱 장소를 순환 배치한 초깃값이며, location_ids에는 Setup에 사용하는 일곱 장소 전체를 이름으로 기록함. 장소 코드는 미확정임.
   - 원본 구성과 적재 전 제한 사항은 `data/game-data/README.md`에 기록함. DB 적재 및 실제 게임 연동은 미검증임.
5. 콘텐츠 원본을 사용자 지정 `data/` 구조로 정리함. 실험은 Day별·유형별 파일로 분리하고 테스트 원본도 `data/test-data/`로 이동함. Setup 외 유형은 빈 배열로 미작성 상태를 표시하며, characters/personas 및 map은 폴더만 준비함. 경로 기준은 `data/README.md`와 PROJECT_STRUCTURE에 반영함.
6. 사용자가 제공한 공통 규칙을 `data/game-data/rules.json`으로 정제하여 작성함.
   - 300초 실험과 술래·도망자 점수 공식, 최초 포획만 인정하는 규칙, 최종 점수 반올림, 30회 누적 순위를 유지함. 중복 설명을 제거하고 기존 기록과 동일하게 최상위 involved_ai·allowed_roles·disclosure_level=full로 정리함. 별도 access 객체와 allowed_ai 필드는 사용하지 않음.
   - 모든 AI와 모든 역할이 원문을 제공받는 공통 규칙임. 현재 DB의 record_id 기반 권한 테이블에 자동 연결되지는 않으며 공통 규칙 로더·권한 연동은 미구현임.
   - 동시 포획 우선순위와 반올림 동률 처리 세부 방식은 임의로 확정하지 않음. 실제 점수 계산·DB 적재·게임 실행은 검증하지 않음.
7. `data/game-data/experiments/day_01/results.json`에 1~5회차 Result를 작성함.
   - 기존 Setup의 술래 배치와 GAME_RULES_V1 공식을 사용해 각 술래가 두 명씩 포획하는 단순한 결과를 구성함. 회차별 전 AI 점수는 32.0~36.0점으로 차이를 작게 두고 계산 점수와 공식 점수는 동일하게 기록함.
   - 포획 시각과 AI별 점수는 content에 작성하고 involved_ai는 전원, allowed_roles는 세 역할 전부, location_ids는 빈 목록으로 지정함.
   - 포획 시각은 시나리오 작성용 설정값이며 실제 실행 측정치가 아님. 이후 Action을 이 포획 결과와 맞춰 작성해야 함. Result에는 포획 결과와 점수를 기록하며, 버그 악용·조작 여부를 단정하는 문구는 제거함.
8. `data/game-data/experiments/day_01/actions.json`의 Action 수를 사용자 지정에 따라 1회차 12건, 2회차 9건, 3회차 10건, 4회차 11건, 5회차 13건으로 조정해 총 55건을 작성함.
   - 이동·은신·탐색·대기·회피 기록을 구성하고 회차별 포획 4건을 유지함. 2회차는 술래 탐색과 첫 포획을 한 기록에 묶음. Setup의 초기 위치와 Result에 지정된 포획자·대상·시각을 유지함. 시각은 content에 실험 경과 초로 기록하고 ID는 기록의 시작 시각순으로 다시 부여함.
   - 목격은 같은 방에 있는 AI로 지정하고 직접 참여자와 분리함. 이동의 location_ids는 출발지·도착지, 포획은 발생 장소를 기록함. 지도 연결 구조는 미확정이므로 방 사이 상세 경로는 확정하지 않음.
   - JSON 재조회로 지정한 회차별 건수와 총 55건, 기존 포획 문장 보존, 고유 ID와 참여자·목격자 중복 없음을 확인함. DB 적재·실제 게임 실행은 미검증임.
9. Day 1 벽 끼임 장면 두 건을 Action과 Incident에 반영함.
   - 3회차 중앙홀에서 YB-2가 27~29초 벽에 겹쳐 멈췄다가 방향을 바꿔 빠져나오며 YB-1이 목격함. 기존 T03-action-002 이동 기록에 장면을 포함함.

11. `data/game-data/experiments/day_01/dialogues.json`에 회차별 3·4·5·4·3건, 총 19건을 작성함.
    - 같은 장소에 있는 AI끼리 은신·경계·추격·포획 후 소감을 대화하도록 구성함. 시각과 장소는 기존 Action과 맞추고, 직접 대화 참여자는 involved_ai, 주변에서 엿들은 AI는 overheard_ai로 분리함. allowed_roles는 세 역할 전부임.
