# O01 - Grafana 보안 감사 대시보드 (선영)

- `infrastructure/docker/docker-compose.grafana.yml`로 Grafana OSS 13.2.0을 별도 실행한다. 로컬 `127.0.0.1:3000`에만 열고 관리자 로그인을 사용한다.
- `setup_grafana_reader.py`로 MariaDB 전용 계정에 `audit_events` SELECT만 부여했다. 로컬에서 감사 테이블 조회 성공과 `users` 조회 거부를 확인했다.
- 데이터 소스와 6개 패널(설명 1개, SQL 5개)을 파일로 프로비저닝했다. 로컬 Grafana `/api/health` 200, 대시보드 등록, 데이터 소스 연결 OK, SQL 패널 5개 실행 성공을 확인했다.
- 임시 `warn` 이벤트가 Grafana의 경고 건수·시간별·캐릭터별·최근 경고 조회에 나타나는지 확인하고 해당 행을 삭제했다. 로그인 페이지는 HTTP 200, 비로그인 대시보드 접근은 로그인으로 이동(302)했다. 브라우저 화면의 시각적 배치는 아직 직접 검사하지 않았다.
- 실제 게임 채팅에서 이벤트가 자동 생성되지는 않는다. 현재 DB가 비어 있다면 숫자 0과 빈 그래프가 정상이며, 정책·검색·출력 이벤트 패널은 아직 없다.

## O02 - 출력 검사 패널 추가 (2026-10-28, 선영 작업 브랜치)

- 기존 대시보드에 Output Guard 이벤트 건수와 최근 판정 메타데이터 표를 추가했다. `signals_json`의 신호 이름·decision·applied만 조회하며 질문·답변 원문은 표시하지 않는다.
- 임시 계정으로 실제 MariaDB에 출력 이벤트 2건이 저장되는 것까지 확인했다. Grafana의 새 패널을 브라우저에서 표시·조회하는 검증은 남아 있다.

## O03 - 웹사이트 관리자 전용 접근 (2026-11-02, 작업 브랜치)

- `015_site_admins.sql`로 웹사이트 관리자 권한을 게임 역할과 분리했다. 기존 계정 `symin123`(로컬 `user_id=2`)에만 로컬 권한을 부여했다. 다른 DB에는 마이그레이션과 권한 부여 명령을 각각 적용해야 한다.
- `/admin/audit`와 Grafana 하위 경로를 KERVION 로그인 세션 및 `site_admins`로 검사한다. Nginx는 검증된 식별자만 Grafana Auth Proxy에 전달한다. Grafana 직접 호스트 포트는 Compose에서 제거했다.
- 로컬 Compose에서 실제 HTTP 요청 결과: 비로그인 사용자는 페이지·Grafana API 모두 401, 일반 계정은 모두 403, 관리자 세션은 페이지 200·Grafana 대시보드 200·대시보드 API 200이다. 위조한 `X-WEBAUTH-USER` 헤더로도 접근이 열리지 않았다. 임시 일반 계정과 시험 세션은 삭제했다.
- 관리자 API·쿠키 단위 테스트 3개 통과, Nginx `nginx -t` 통과, `node --check frontend/app.js` 통과. Grafana가 프록시 계정 `kervion-2`를 인식하고 대시보드 UID를 반환했다.
- 실제 로그인 UI에서 대시보드 메뉴를 눌러 보는 브라우저 시각 검증과 Kubernetes/AWS 배포는 아직 하지 않았다.
- 관리자 화면의 왼쪽 메뉴·상단 안내·검사 영역 안내 카드·Grafana 프레임을 KERVION 색감에 맞게 정리했다. 안내 카드에는 예시 숫자를 넣지 않고 실제 Grafana 패널만 데이터를 표시한다. 로컬 HTML 배치를 Chrome에서 시각 확인했고, 변경 후 관리자·일반 계정·비로그인 HTTP 접근 결과와 관리자 단위 테스트 3개를 다시 확인했다.

## O04 - 정책 거부 패널 (2026-11-02, 선영 작업 브랜치)

- `policy_denial`의 이벤트 건수 패널과 최근 사유·단계·거부 기록 수 표를 추가했다. 관리자 화면 안내 카드에도 정책 거부 항목을 표시한다.
- Grafana의 관리자 프록시 API에서 두 패널(ID 9, 10) 등록을 확인했다. 로컬 `AI_SCOPE` 이벤트 1건을 만들고 Grafana 데이터 소스의 건수 쿼리가 1건, 상세 표 쿼리가 사유·단계·거부 기록 수를 반환하는 것을 확인한 뒤 시험 행과 시험 세션을 삭제했다. 같은 초에 만든 이벤트는 Grafana 시간 필터 상한의 초 단위 절삭 때문에 다음 새로고침 전까지 잠깐 0으로 보일 수 있다.
- 사유별 집계 표(ID 11)를 추가했다. 임시 이벤트 2건에 `FUTURE_DAY:2`, `ROLE_DENIED:1`, `AI_SCOPE:1`을 넣어 Grafana가 사유별 이벤트 수는 각각 1건, 거부 기록 수는 2·1·1건으로 분리 집계하는 것을 확인했다. 이벤트가 없는 사유도 0건 행으로 남도록 SQL을 구성했다. 관리자 대시보드 API에서 패널 9·10·11 등록을 확인하고 시험 이벤트·세션을 삭제했다.

# O05 - Discord 보안 감사 알림 (2026-11-03, 선영)

1. 선택 실행용 `docker-compose.discord.yml`과 알림 규칙 3개·연락처 3개를 추가했다. 웹훅 URL은 로컬 환경변수로 전달하며 저장소에는 빈 예시 값만 둔다.
2. 입력·출력·정책 메시지를 판정·처리·신호·요청 ID로 통일했다. 제목의 색과 처리 유형을 구분하며, 입력 `role_or_state_override`는 초록색으로 표시해도 `high_risk`와 고정 응답 처리는 유지한다. 본문 위쪽에만 여백 문자를 둔다.
3. 로컬 MariaDB에서 알림 SQL 3개 실행과 Grafana 규칙 감지를 확인했다. 입력 규칙 검사·감사 저장으로 입력 알림을 만들고, 출력·정책에는 형식 확인용 모의 감사 이벤트를 저장하여 7종 알림을 시험했다. Discord 연락처의 전송 오류가 없음을 확인했고 사용자가 실제 수신·표시를 확인했다. 시험 데이터는 사용자 요청에 따라 남겼다. 실제 캐릭터 생성부터의 전체 출력·정책 E2E 검증을 뜻하지 않는다.
4. 위쪽 여백 형식은 Grafana 템플릿 미리보기에서 시작 공백 줄과 끝 줄바꿈 제거를 확인했다. 마지막 시험 요청 `notify_top_6a5d9af6`의 전송 성공을 확인했고, 사용자가 형식을 확인한 뒤 커밋·푸시를 요청했다. Kubernetes·AWS 배포와 외부 환경의 Discord 전송은 이번 검증에 포함하지 않는다.
