# E01 - Qdrant 색인과 권한 범위 검색

1. 용범(C·F)과 검색 계약을 정하고 `docs/interfaces/RAG_검색_계약.md`에 적는다.
2. MariaDB의 게임 기록을 읽어 Qdrant에 색인한다. 공개 수준별로 `meta`·`summary`·`content` 점을 따로 만든다.
3. 긴 글은 모델 한도(128토큰)를 넘지 않게 나눈다. 잘리는 글이 없어야 한다.
4. 색인할 때 MariaDB 체크섬을 manifest에 남기고, 검색할 때 비교해 오래된 색인은 쓰지 않는다.
5. 검색: `search_scope` → 허용 ID 안에서 수준에 맞는 점만 검색 → `resolve` 결과만 반환. Planner 조건은 좁히기만 한다.
6. 시험: 허용 밖 기록, 낮은 수준 기록의 본문 검색, 조건별 좁히기, 잘못된 요청, 오래된 색인, 글 나누기.

# E02 - 채팅 파이프라인 연동

1. 용범이 만든 채팅 POST 파이프라인(`backend/api/chat_pipeline.py`)이 RAG를 어떻게 부르는지 확인한다. 채팅마다 `FastEmbedder()`를 새로 만드는 점이 느리다.
2. 모델을 프로세스당 한 번만 올린다.
3. 결과가 빈 이유(허용된 기록 없음 / 맞는 기록 없음)를 신호로 돌려준다. 기존 `search_records`는 그대로 둔다.
4. 허용된 기록을 D의 `memory`(`[{id, text}]`)로 바꾸는 함수를 만든다.
5. 계약 문서 9절과 시험을 갱신한다. 다른 담당자의 파일(`chat_pipeline.py`·D 코드)은 바꾸지 않고 연결 방법만 적는다.

# E03 - 검색 품질 측정과 메타데이터 머리글

1. 실제 DB·Qdrant로 검색 품질을 잰다. 질문 788개(`experiments/rag/build_cases.py`)를 역할별(교수·대학원생·학부 연구생)로 돌려 hit@1·3·5와 MRR을 본다. 허용 밖 기록이 한 건이라도 나오면 위반으로 센다.
2. 질문은 세 가지로 나눈다. `filtered`는 Planner가 조건을 정확히 준 경우, `broad`는 "첫날"처럼 날짜 범위만 준 경우, `plain`은 조건 없이 질문만 보낸 경우다.
3. 요약이 "YB-2 이동 및 은신."처럼 장소·회차가 없어서 요약 수준 역할은 이런 질문을 못 찾는다. 색인할 때 요약·본문 조각 앞에 기록 메타데이터(유형·Day·시험·장소·관련 AI)를 붙인 `header` 모드를 시험한다. 그 수준에서 이미 볼 수 있는 필드만 쓴다.
4. 효과가 있으면 `header`를 기본으로 한다. `plain`도 고를 수 있게 둔다.
