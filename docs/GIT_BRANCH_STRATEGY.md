# Git 브랜치·PR 운영안

> 작성일: 2026-10-22  
> 상태: **팀 합의 전 논의 초안**  
> 대상 저장소: `kcg020529/detective.game.github.io`  
> 이 문서는 선영과의 논의에서 나온 **팀 검토용 권장안**이다. 브랜치 보호 규칙이 적용되었다는 뜻은 아니다. `.github/CODEOWNERS`는 현재 작업 브랜치에 초안으로 있으며, `main`에 병합되기 전에는 자동 검토 요청에 사용되지 않는다.

**추천 방식:** GitHub-flow에 가깝게 `main` + 작업 단위 브랜치 + PR로 운영한다. A~O를 각각 유지하는 브랜치로 만들지 않는다. 현재 프론트엔드는 `main`의 `frontend/` 변경 시 GitHub Pages에 배포된다. 백엔드까지 자동 배포된다는 뜻은 아니다.

## 1. Part와 브랜치의 관계

프로젝트는 A~O 대분류로 담당 범위와 `PLAN.md`·`RESULT.md`를 관리한다. `WORKFLOW.md`에 따르면 Part ID는 기능을 찾아보기 위한 **문서 라벨**이며 고정 개발 순서가 아니다. 따라서 **Part 하나마다 계속 유지하는 브랜치를 만들지 않는다**는 방식을 제안한다.

브랜치는 **한 PR에서 검토하고 병합할 수 있는 작업 묶음**으로 만든다. 한 작업이 F·I처럼 여러 Part에 걸칠 수 있고, 같은 I 안에서도 Save API와 채팅 API를 독립적으로 검토할 수 있으면 나눌 수 있다. 작업 규모를 기준으로 판단한다.

## 2. 기본 흐름 (팀 검토용 권장안)

1. `main`을 병합된 작업의 기준으로 둔다. 새 작업 전에 원격의 최신 `main`을 확인한다.
2. 최신 `main`에서 작업 브랜치를 만든다. 팀원이 동시에 수정 중인 공통 파일과 계약을 확인한다.
3. 관련 변경만 커밋하고, 실제 테스트 결과와 미완료 사항을 PR 설명에 적는다. `RESULT.md`는 실제 구현·검증 후에만 작성한다.
4. **모든 변경은 PR로 `main`에 병합한다. 긴급 수정도 작은 `fix/` 브랜치와 PR을 사용하며 직접 push 예외는 두지 않는다.** 이는 이 대화에서 정한 운영 방식이다.
5. 병합 후 작업 브랜치를 삭제한다. **병합 전에는 삭제하지 않는다.** 병합된 변경과 PR 기록은 남는다.

예시 명령(브랜치명은 작업에 맞게 변경):

```bash
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feat/F-policy-engine
# 작업·검증 후 관련 파일만 git add, git commit
git push -u origin feat/F-policy-engine
# GitHub에서 PR 생성·검토·병합
```

`main`에 직접 작업하지 않는 것을 제안한다. 이미 `main`에 로컬 커밋을 만들었더라도 커밋을 보존할 새 브랜치를 먼저 만든 뒤 `main` 위치를 정리한다. 커밋을 버리는 방식으로 해결하지 않는다. **GitHub에서 직접 push를 기술적으로 막을지는 아직 결정하지 않았다.**

## 3. 브랜치 이름 (제안)

형식: `종류/작업-설명`. 설명은 짧은 영문과 하이픈을 쓴다. `feat/`의 기능 타입은 담당 대분류 코드(A~O)를 뜻한다. 한 작업이 여러 Part에 걸치면 Part 코드 대신 기능명을 사용할 수 있다. **`docs/` 브랜치에는 작성자 약칭을 작업 설명 앞에 붙인다**(예: 선영 `sym`). 다른 종류는 Part 코드나 기능명으로 작업 범위를 나타내며 담당자 약칭은 필수로 두지 않는다.

| 접두어 | 용도 | 예시 |
|---|---|---|
| `feat/` | 새 기능; `feat/<기능-타입>-<작업>` (`기능-타입` = A~O Part 코드) | `feat/F-policy-engine`, `feat/I-save-api` |
| `fix/` | 오류 수정 | `fix/save-ownership` |
| `docs/` | 문서·공유 계약; `docs/<작성자-약칭>-<작업>` | `docs/sym-api-policy-drafts` |
| `test/` | 테스트·보안 실험 | `test/L-role-bypass` |
| `chore/` | 개발 환경·설정 | `chore/K-compose` |

현재 존재하거나 과거 사용한 브랜치를 이름만 맞추려고 일괄 변경할 필요는 없다. **새 작업부터 적용**하면 된다. 접두어보다 PR의 작업 범위가 명확한지가 더 중요하다.

## 4. 커밋과 PR 범위 (제안)

- 커밋은 변경 이유를 알 수 있게 쓴다. 한 파일씩 커밋해야 하는 규칙은 없지만, 독립적인 변경은 분리한다.
- PR은 팀원이 검토할 수 있는 크기로 유지한다. 관련 없는 수정이 섞이면 별도 브랜치·PR로 나눈다.
- PR 설명에는 **목적, 변경 파일·계약, 실제 실행한 테스트, 남은 결정 사항**을 적는다. 실행하지 않은 테스트는 통과로 쓰지 않는다.
- `docs/interfaces/`의 API·정책 문서는 구현과 합의 상태를 구분한다. `parts/<대분류>/RESULT.md`에는 실제로 구현·검증한 내용만 기록한다.
- 다른 사람이 먼저 구현한 인터페이스를 바꿀 때는 해당 코드를 쓰는 사람과 영향 범위를 확인한다.

### PR 병합 방식

**일반 병합을 기본값으로 한다.** 의미 있게 나눈 작업 커밋은 `main`에도 각각 남긴다. 한 작업을 진행하며 쌓인 자잘한 수정·정리 커밋만 있는 PR은 작성자와 병합자가 확인한 뒤 **스쿼시 병합**할 수 있다. 병합 방식은 사람별로 다르게 정하지 않고 PR의 커밋 내용으로 판단한다.

## 5. 리뷰·승인 규칙 (현재 권장안)

취업 포트폴리오 프로젝트인 현재 단계에서는 **필수 승인 설정을 켜지 않는다**는 운영 방식을 논의했다. PR은 변경을 확인하고 의견을 남기는 장소로 사용한다. 작성자는 저장소 설정이 허용하면 승인 없이 직접 병합할 수 있다.

| 변경 유형 | 검토 제안 |
|---|---|
| 인증, Save 소유권, 권한 정책, 검색 ACL, 공통 데이터·API 계약 | 관련 담당자에게 검토 요청하고 의견을 확인 |
| 여러 Part가 함께 사용하는 코드·스키마 | 영향을 받는 담당자에게 리뷰 요청 |
| 독립적인 화면 수정·오탈자 | PR 변경 내용과 실제 테스트 결과 확인 |

이 검토 요청은 **승인 요청이나 병합 차단 규칙이 아니다**. 팀이 나중에 필수 승인을 원할 때만 `main`의 브랜치 보호 규칙 또는 Ruleset에서 별도로 설정한다.

### 다른 담당자 영역 수정과 `CODEOWNERS`

`.github/CODEOWNERS` 초안에는 A~O와 주요 코드 경로별 팀원 GitHub 아이디를 적었다. 이는 Git 커밋의 원래 작성자가 아니라 **PR에서 변경된 파일 경로**를 기준으로 담당자에게 검토 요청을 보내기 위한 것이다. **현재 파일은 작업 브랜치에만 있어 작동 전**이며, PR 대상 브랜치인 `main`에 병합된 뒤 새 PR부터 사용된다. 담당자에게 쓰기 권한이 있어야 자동 요청이 유효하다.

`CODEOWNERS`만으로 승인 의무가 생기지는 않는다. **코드 소유자 리뷰 필수**를 별도로 켜면 담당자 자신의 PR은 본인이 승인할 수 없어 막힐 수 있으므로, 현재 방식에서는 그 설정을 켜지 않는다. 담당자 외에 의견을 듣고 싶은 사람이 있으면 해당 PR에서 별도로 언급할 수 있다. 모든 PR에 `@AnbyMata`를 언급하는 규칙은 정하지 않았다.

## 6. 팀 검토 항목

- [ ] **적용 전 확인:** `CODEOWNERS`의 경로별 계정에 저장소 쓰기 권한이 있는지 확인하고 파일을 `main`에 병합
- [ ] **미정:** PR에서 필수로 통과해야 할 자동 검사(테스트·빌드)를 둘지
- [ ] **미정:** 병합된 브랜치의 자동 삭제 설정

팀 검토 후 합의한 항목만 확정으로 바꾸고 실제 GitHub 설정과 일치하는지 확인한다. 현재 저장소에서 확인한 워크플로는 `main`의 프론트엔드 변경을 Pages에 배포하는 작업이며, PR용 공통 테스트 워크플로는 확인되지 않았다.
