# API 요청·응답 계약

> 작성일: 2026-10-21 · 상태: **팀 합의 전 초안**  
> 기준: `MASTER.md`, `PARTS.md`, `WORKFLOW.md`, `PROJECT_STRUCTURE.md`, `parts/J-frontend/RESULT.md`  
> 주 담당: I(백엔드, 선영) · 협의: J(프론트엔드), A(게임 규칙), B(DB), C/D/E/F/G/H  
> 관련 정책: [역할별 권한 매트릭스](역할별_권한_매트릭스.md)

이 문서의 API 경로·필드·상태 코드는 모두 **제안**이다. 현재 J 화면의 로그인·Save·채팅·Day 진행·판정은 Mock/브라우저 메모리 기반이며 실제 백엔드 API 연결은 확인되지 않았다. 조사 토큰 표시·차감·질문 제한은 프론트엔드에서 제거되었다. 실제 구현과 합의가 생기면 이 문서를 갱신한다.

**게임 규칙 (`MASTER.md`·J02 구현 기록 확인):** 플레이어가 **“다음날” 버튼을 누르면 현재 Save의 Day가 다음 Day로 진행**한다. **조사 토큰 시스템은 사용하지 않는다.** Day 6을 초과해 진행하지 않으며, J 화면에서는 Day 6에 버튼을 비활성화했다. 서버도 Day 6 초과 요청을 거부해야 한다.

## 1. 문서에서 확정된 보안 경계

- 인증된 사용자와 Save 소유권, 현재 Day, 역할은 서버의 신뢰된 상태에서 확인한다. 요청 본문의 주장이나 Planner 출력으로 권한을 높이지 않는다.
- `save_id`는 대상 식별자일 뿐 소유권 증명이 아니다. Save별 요청마다 소유권을 검사한다.
- 채팅은 Input Guard → Planner → Policy Engine → ACL 검색·결과 재검증 → 캐릭터 응답 → Output Guard 순서의 서버 흐름을 따른다.
- 정책 또는 검색에 필요한 메타데이터가 없거나 검증에 실패하면 기본 거부한다. 실제 접근 정책은 [역할별 권한 매트릭스](역할별_권한_매트릭스.md)를 따른다.

## 2. 공통 요청·응답 규약 (제안)

- Base path: `/api/v1`; JSON UTF-8; 필드명 `snake_case`.
- 인증 방식(쿠키 세션 또는 인증용 Bearer 토큰)은 I·J 합의가 필요하다. 여기서 인증용 토큰은 **삭제하기로 한 게임의 조사 토큰과 별개**다. 비밀번호를 채팅·Save 요청에 재전송하지 않는다.
- 클라이언트는 `role`, `current_day`, `owner_user_id`를 인가용 입력으로 보내지 않는다. 서버 응답의 표시 정보로만 사용한다. 게임 상태에 조사 토큰 잔액 필드를 두지 않는다.
- 서버가 `request_id`를 생성 또는 검증해 응답·감사 이벤트에 연결한다. `client_request_id`는 재시도 중복 방지를 위한 제안 필드이며 권한 근거가 아니다.
- 플레이어에게는 비공개 문서 ID, 내부 정책 세부 판정, 원문 Context를 반환하지 않는다.

오류 응답 예시:

```json
{
  "error": {
    "code": "ACCESS_DENIED",
    "message": "이 기록은 현재 열람할 수 없습니다.",
    "request_id": "req_01"
  }
}
```

| HTTP 상태 | 제안 용도 | 제안 코드 |
|---|---|---|
| 400 | 요청 형식 오류 | `INVALID_REQUEST` |
| 401 | 인증 없음·만료 | `AUTH_REQUIRED` |
| 403 | 소유권·정책 위반 | `ACCESS_DENIED` |
| 404 | 없거나 존재 여부를 감춰야 하는 리소스 | `NOT_FOUND` |
| 409 | 게임 상태 충돌·중복 요청 | `STATE_CONFLICT` |
| 422 | 입력 유효성 오류 | `VALIDATION_ERROR` |
| 503 | 정책·검색 서비스 장애로 안전한 처리 불가 | `SERVICE_UNAVAILABLE` |

403/404의 외부 응답 기준은 F·I가 정한다. 구체적 거부 이유는 권한이 제한된 감사 이벤트에 기록한다.

|---|---|---|---|---|
| 로그인 | `POST /api/v1/auth/login` | `username`, `password` | 사용자 식별자, 인증 상태 | J·B |
| 내 정보 | `GET /api/v1/auth/me` | 인증 정보 | `user_id`, 표시 이름 | J·B |
| Save 목록 | `GET /api/v1/saves` | 인증 정보 | 본인 Save의 ID·역할·Day·갱신 시각 | J·B |
| 새 게임/Save | `POST /api/v1/saves` | 선택할 `role` | 서버가 만든 Save ID·역할·Day | J·A·B |

| 채팅 | `POST /api/v1/saves/{save_id}/chats` | 캐릭터 ID·질문·재시도 ID | 최종 대사·표시 종류·갱신 상태 | J·C·D·E·F·G·H |
| 다음날 버튼 | `POST /api/v1/saves/{save_id}/advance-day` | Save ID, 필요 시 상태 버전 | 갱신된 Day·게임 상태 | J·A·B |

### 게임 안에서 일어나는 행동

화면의 모든 클릭에 API가 필요한 것은 아니다. 창 열기·닫기, 창 이동, 캐릭터 탭 전환처럼 **화면 모양만 바꾸는 행동**은 프론트엔드가 처리한다. 반면 서버의 게임 상태를 읽거나 바꾸는 행동과 보호된 기록 열람은 서버 API가 필요하다. 아래는 현재 화면과 프로젝트 요구사항을 연결한 **설계 목록**이다.

| 플레이어 행동 | 처리 제안 | 서버가 확인할 것 | 현재 상태 |
|---|---|---|---|
| 출입증 선택·이어서 조사 | Save 목록·상태 조회 API | 로그인 사용자와 Save 소유권 | 화면 Mock |
| 새 수사 시작·기존 슬롯 덮어쓰기 | Save 생성/초기화 API | 소유권·역할 선택·덮어쓰기 규칙 | 화면 Mock, 서버 규칙 미정 |
| AI 선택·질문 | 채팅 API | Save 소유권, 실제 역할·Day, AI Scope, 검색 ACL | 예시 답변 Mock |
| 기록 보관함에서 파일 열람 | **별도 기록 목록/상세 API 제안** | 문서 등급·공개 Day·Save 범위; 기록 열람 경로의 정책 | 화면 예시 데이터만 있음 |
| 단서 수첩 보기 | 단서 목록 API 제안 | Save 소유권 | 화면 메모리 값 |
| 수첩 메모 작성·수정 | Save별 메모 저장 API 제안 | Save 소유권 | 화면 메모리 값, 서버 미연결 |
| 대화·기록에서 단서 발견 | 채팅/기록 열람 처리 결과에 단서 추가를 포함할지 결정 | 중복 획득·Save 귀속·획득 조건 | 화면에서 로컬 추가 |
| “다음날” 버튼 누르기 | 서버가 현재 Save의 Day를 다음 Day로 갱신하는 API 제안 | Save 소유권·서버의 현재 Day·Day 6 상한·중복 클릭 방지 | 화면 동작 구현, 서버 미연결 |
| 범인 지목·최종 추리 제출 | 제출 API 제안 | Save 소유권·제출 가능 시점·재제출/종료 규칙 | 화면 예시 판정 구현, 서버 판정 미연결 |

기록 열람 API의 경로 예시는 `GET /api/v1/saves/{save_id}/records`와 `GET /api/v1/saves/{save_id}/records/{record_id}`이다. 목록에서 잠금 표시를 하더라도 **상세 조회에서 서버가 다시 인가**해야 한다. 목록이 비공개 기록의 존재나 제목을 보여줘도 되는지 F·A·J가 결정해야 한다.

데이터가 메타데이터·요약본·자연어 원문의 세 부분으로 구성된다는 사용자 전달 사항이 있다. 기록 목록에서 요약본을 반환할지, 상세 조회에서 원문을 반환할지, 채팅용 검색에서 어느 부분을 사용할지는 B·E·F·I가 합의해야 한다. **요약본도 내용이므로 인가 전에는 반환하지 않는다.** 세 부분의 정확한 필드·저장 위치·개별 등급은 확인 전이다. 자세한 정책 고려사항은 [역할별 권한 매트릭스](역할별_권한_매트릭스.md)를 따른다.

단서 API의 경로 예시는 `GET /api/v1/saves/{save_id}/clues`, 최종 추리 제출은 `POST /api/v1/saves/{save_id}/accusations`이다. 단서 획득을 독립 API로 둘지 채팅/기록 열람의 서버 결과로 처리할지는 게임 규칙 합의가 필요하다. **클라이언트가 임의의 단서 ID·Day를 보내 서버 상태를 직접 바꾸는 계약은 제안하지 않는다.**

“다음날” 버튼은 서버에 Day 진행을 요청하고, 서버가 저장된 Day를 갱신한 뒤 새 게임 상태를 반환하도록 제안한다. 프론트엔드는 반환된 Day를 표시한다. 클라이언트가 `current_day: 2`처럼 원하는 Day를 보내 덮어쓰는 방식은 사용하지 않는다. Day 범위는 1~6이며, Day 6에서는 화면 버튼을 비활성화하고 서버도 진행 요청을 거부한다. 구체적인 오류 코드·문구는 I·J가 합의한다.

로그아웃, Save 덮어쓰기·삭제의 세부 계약은 인증·게임 규칙 합의 후 추가한다. J 화면의 Save 3칸은 현재 구현된 UI 값이며 서버 슬롯 규칙으로 확정하지 않았다. 조사 토큰 표시·질문 제한 로직은 J 화면에서 제거되었고 API에도 해당 필드를 두지 않는다.

### 채팅 요청·응답 예시 (제안)

```http
POST /api/v1/saves/save_123/chats
Content-Type: application/json
```

```json
{
  "character_id": "YB-1",
  "message": "첫날 실험에서 무엇을 봤어?",
  "client_request_id": "ui_01"
}
```

```json
{
  "request_id": "req_01",
  "save_id": "save_123",
  "character_id": "YB-1",
  "reply": "제가 확인한 첫날 기록은 …",
  "reply_kind": "normal",
  "game_state": {"current_day": 1}
}
```

`reply_kind` 제안 값은 `normal`, `redacted`, `access_denied`, `unknown`이다. J의 표시 종류에 대응한다. 내부의 검색 문서·LLM Context·정책 판정은 플레이어 응답과 분리한다.

## 4. 합의할 항목과 완료 기준

- [ ] I·J: 인증 방식, 화면이 필요한 응답 필드, `reply_kind`, 오류 문구·403/404 처리.
- [ ] I·A·B·J: 서버의 Day 진행·Day 6 상한과 중복 클릭 처리 방식, Save 생성·덮어쓰기 규칙을 정한다.
- [ ] I·J: 수첩 메모·단서·판정서의 서버 저장·응답 계약을 정한다. API에 조사 토큰 필드를 사용하지 않는다.
- [ ] I·A·J: 기록 보관함·단서·최종 추리 행동의 API 범위와 게임 결과 규칙.
- [ ] I·F·E: 채팅에서 검증된 상태를 정책·검색에 전달하는 내부 계약.
- [ ] I·H: `request_id`, 사용자·Save·역할·캐릭터, 정책·검색·마스킹 결과의 감사 이벤트 계약.
- [ ] 실제 API·DB 연결 및 테스트 결과가 없으면 구현 완료로 기록하지 않는다.

공유 계약은 `docs/interfaces/`에 두고, 실제 작업·검증 결과는 해당 `parts/<대분류>/PLAN.md`·`RESULT.md`에 사실대로 기록한다.
