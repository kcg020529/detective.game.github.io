# 역할별 권한 매트릭스

> 작성일: 2026-10-21 · 상태: **팀 합의 전 초안**  
> 기준: `MASTER.md`, `PARTS.md`, `WORKFLOW.md`, `PROJECT_STRUCTURE.md`, `parts/J-frontend/RESULT.md`  
> 주 담당: F(접근통제, 선영) · 협의: A(게임·AI 지식), B(DB·메타데이터), E(RAG), I(백엔드), J(화면)  
> 관련 API: [API 요청·응답 계약](API_요청응답_계약.md)

## 1. 문서상 확정된 정책

- 역할 키와 명칭: `prof` 교수, `grad` 대학원생, `std` 학부 연구생. **등급별 세부 권한은 아직 설계 필요**하다.
- 허용 Context = **선택 AI Knowledge Scope ∩ 플레이어 역할/문서 등급 ∩ 현재 Day ∩ 사용자 Save**. 네 조건 모두 통과해야 한다.
- 역할·Day·Save 소유권은 인증 정보와 신뢰된 저장소에서 확인한다. 사용자 질문, 프론트엔드 값, Planner 출력은 권한 증명이 아니다.
- Qdrant 검색 전 권한 메타데이터로 필터링하고 반환 문서를 다시 검사한다. 메타데이터 누락, 정책 판정 실패, 검색 장애 시 기본 거부한다.
- 검색 가능한 문서가 없다는 이유로 전체 문서를 LLM Context에 넣는 무제한 대체 검색을 하지 않는다.
- 검색된 문서, LLM Context에 전달된 문서, 최종 응답에 노출된 정보는 구분해 검증한다. 최종 마스킹만으로 앞 단계 비인가 검색이 정당화되지 않는다.

## 2. 역할 × 등급 허용표 (합의용 제안)

`L1`~`L3` 이름·의미와 아래 허용칸은 **확정 정책이 아니다**. J 화면은 `prof > grad > std`의 예시 열람 순서를 사용하지만 F의 서버 정책은 아직 확정되지 않았다.

| 역할 \ 문서 등급 | `L1` 일반 기록 | `L2` 연구 기록 | `L3` 제한 기록 |
|---|---|---|---|
| `std` 학부 연구생 | 허용 제안 | 거부 제안 | 거부 제안 |
| `grad` 대학원생 | 허용 제안 | 허용 제안 | 거부 제안 |
| `prof` 교수 | 허용 제안 | 허용 제안 | 허용 제안 |

**허용칸도 최종 허용을 뜻하지 않는다.** Day, Save, 선택 AI의 Knowledge Scope를 모두 통과해야 한다. 교수도 미래 Day 문서·타인 Save·선택 AI가 모르는 문서는 볼 수 없다. 게임 비밀은 정상 조건을 만족하면 발견 가능해야 하며, 비인가 보안 기밀과 구분한다.

## 3. 판정 규칙 (제안 표현)

```text
요청의 user_id, role, save_id, current_day를 서버의 인증·저장 상태에서 조회
문서의 필수 인가 메타데이터 존재 여부 확인 → 누락 시 거부
역할 × 문서 등급 허용표 확인 → 불허 시 거부
document.release_day <= save.current_day 확인 → 미래 문서 거부
전역 문서 또는 현재 사용자가 소유한 Save 범위인지 확인 → 타인 Save 거부
선택 character_id가 문서 Knowledge Scope에 있는지 확인 → 모르면 거부
모든 검사가 성공하면 해당 문서만 검색 결과와 LLM Context 후보로 허용
```

제안 메타데이터: `document_id`, `security_level`, `release_day`, `scope_type`(`global`/`save`), `owner_save_id`(Save 전용), `known_by_character_ids`. 필드명·null 허용·전역 기록 표현·MariaDB와 Qdrant 간 정합성은 B·E와 합의한다. 이 문서는 DB 스키마가 이미 구현됐다는 뜻이 아니다.

### 기록의 세 부분과 권한 적용

**2026-10-21 사용자 전달 사항:** 데이터에는 **권한 판단 등에 쓰는 메타데이터**, **요약본**, **자연어로 작성된 실제 기록**의 세 부분이 있다고 한다. 이는 데이터 담당자가 전달한 구조로 기록하며, 세 부분의 물리적 저장 위치·필드명·서로 다른 등급 여부는 아직 확인되지 않았다.

| 부분 | 용도 해석 | 권한 처리 제안 |
|---|---|---|
| 메타데이터 | 기록 ID, 등급, 공개 Day, Save 범위, AI 지식 범위 등 | 검색 전 필터와 검색 후 재검증의 근거. 누락 시 기본 거부 |
| 요약본 | 검색·Planner·LLM Context에 사용할 수 있는 짧은 내용 | **원문보다 자동으로 낮은 등급으로 취급하지 않음**. 플레이어/AI에게 전달하기 전 같은 인가 조건 적용 |
| 자연어 원문 | 실제 사건·대화 등의 상세 기록 | 보관함 열람·LLM Context 전달 전 인가 확인. 요약이 허용됐다는 사실만으로 원문 열람 허용하지 않음 |

요약본과 원문이 각각 다른 공개 범위를 가져야 한다면, B·F·E가 **각 부분의 등급·공개 Day·AI Scope를 명시적으로 따로 정의**해야 한다. 그 전에는 동일 기록의 요약본과 원문 모두 해당 기록의 보호 조건을 따른다는 보수적 제안으로 둔다. 각 부분은 같은 `document_id` 또는 검증 가능한 연결 ID로 매칭하고, 서로 다른 기록의 메타데이터가 섞이지 않도록 적재·검색 시 검사한다.

## 4. 확인 시나리오

| 시나리오 | 기대 판정 |
|---|---|
| 허용 등급 + 공개 Day + 본인 Save/전역 + 선택 AI가 앎 | 허용 |
| 역할 등급 초과 | 거부 |
| Day 1에서 Day 2 이후 공개 기록 요청 | 거부 |
| 다른 사용자의 Save 전용 기록 요청 | 거부 |
| 선택 AI가 모르는 기록 요청 | 거부 |
| 역할 사칭 문장을 프롬프트에 포함 | 서버 역할 유지, 권한 상승 거부 |
| 인가 메타데이터 누락·정책 오류·검색 장애 | 기본 거부 |

정책 단위 테스트와 E의 검색 전 필터·검색 후 재검증 테스트를 분리한다. 실제 테스트 전에는 통과로 표시하지 않는다.

2. A·B·F: AI Knowledge Scope를 문서별로 어떻게 정의하고 변경할 것인가?

4. B·E·F: 요약본과 자연어 원문은 어디에 저장되며, 각각 별도 권한·공개 시점을 갖는가? 검색 결과에 어느 부분을 포함할 것인가?
5. F·I: 권한 거부를 API 403/404 및 플레이어용 `reply_kind`에 어떻게 매핑할 것인가? 내부 감사 사유는 어떻게 기록할 것인가?
6. F·J: UI 잠금 표시는 서버 권한 판정을 어떻게 반영할 것인가? 화면의 숨김만으로 접근통제를 완료했다고 보지 않는다.

합의된 정책은 이 문서에 날짜와 합의자를 기록해 갱신한다. 변경 시 I API, E 검색 필터, B 데이터, J 표시와 테스트의 정합성을 확인한다.
